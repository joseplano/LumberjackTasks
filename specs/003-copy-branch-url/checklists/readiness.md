# Pre-Implementation Readiness Checklist: Copy the branch URL, not just the branch name

**Purpose**: Validate that the requirements for this feature are complete, unambiguous, and mutually consistent **before** any production code is written
**Created**: 2026-08-16
**Feature**: [spec.md](../spec.md)
**Depth**: Formal pre-implementation gate
**Audience**: The implementing agent and the human reviewer, before implementation starts

> These items test the **requirements**, not the implementation. Every item asks whether something is adequately *written down*, not whether code does it.

- [x] CHK002 - Is the transformation from the stored repository value to a repository address defined step by step, including the order of the steps? [Completeness, Spec §FR-003/FR-003a/FR-003b, research.md §R3]
- [x] CHK003 - Is a URL shape defined for every forge named in scope, plus for hosts that match none of them? [Coverage, Spec §FR-005/FR-003d, contracts/branchUrl.md §Stage 2]

## Requirement Clarity

- [x] CHK008 - Is "the label" resolved into the exact attributes that change, so it cannot be read as the visible button text? [Clarity, Ambiguity, Spec §FR-006 and §Clarifications, research.md §R9]
- [x] CHK009 - Is the encoding rule stated per URL position (path segment versus query parameter) rather than as a single global rule? [Clarity, Spec §FR-005a, research.md §R6]
- [x] CHK010 - Is the exact literal text of both control names specified, including capitalisation? [Clarity, Spec §FR-006, §User Story 2 scenarios 3-4]
- [x] CHK011 - Is the difference between "no repository URL" and "a repository URL that is not usable" defined, and do both lead to a stated outcome? [Clarity, Spec §FR-003c/FR-004, §Edge Cases]
- [x] CHK012 - Is the order-dependence of `.git`-stripping and trailing-slash-stripping made explicit, given that the reverse order changes the result for `…/repo.git/`? [Clarity, Spec §FR-003b, research.md §R3, contracts/branchUrl.md §Stage 1]
- [x] CHK013 - Is the query-parameter append rule defined for a repository address that already carries a query string? [Clarity, Spec §FR-005a, §Edge Cases, contracts/branchUrl.md §Stage 2] — deliberately scoped to the query-parameter forge; the complementary path-shape case is CHK031, which was missing until 2026-08-17
- [x] CHK031 - Is the treatment of a query string or a fragment on the stored repository URL defined for **both** URL shapes — discarded where the branch is placed in a path, preserved where the branch is placed in a query — rather than for only one of them? [Clarity, Conflict-check, Spec §FR-003/FR-003e, §Edge Cases, contracts/branchUrl.md §Stage 1 rules 6a-6b] — added by the rulings of 2026-08-17. The final rule divides by URL **component**, not by forge: the fragment is discarded on every shape (6a) and the query only on the path shapes (6b), which the rule names explicitly, with the Azure DevOps query exemption and its reason stated in both the spec and the contract. The contract gives worked examples for a query, a fragment, both together, a query masking a `.git` suffix, and — on the query-parameter forge — a fragment, a fragment with a query, and the legacy `visualstudio.com` hash form
- [x] CHK032 - Is the ordering interaction between the query/fragment discard and the `.git`/trailing-slash removal made explicit, given that a query can hide a trailing `.git` from the earlier rules? [Clarity, contracts/branchUrl.md §Stage 1 rules 3, 4 and 6c] — rule 6c re-applies rules 3 and 4 to whatever 6a and 6b leave, on every shape rather than only the path ones, so `https://host/o/r.git?tab=readme` reduces to `https://host/o/r`, which is what FR-003b requires of every form of that address. Rule 3's wording was also corrected: read literally it previously did not reduce `…/repo.git/` to `…/repo`, though the shipped code and its tests always did

## Requirement Consistency

- [x] CHK014 - Does any success criterion state universally something that an edge case is permitted to violate? [Conflict-check, Spec §SC-001 vs §Edge Cases] — SC-001 is scoped to the four named forges, and the unrecognised-host edge case is deliberately excluded from it; SC-004 is universal and holds in every branch of the logic because the name and the payload come from one evaluation. **Re-evaluated 2026-08-17**: this item was previously checked while an unrecorded input class made it false — a stored URL carrying a query or a fragment on a path-shaped forge broke SC-001's "100%" while no edge case named it. The human partner's ruling (spec §Clarifications, Session 2026-08-17) added FR-003e and the matching edge case, so SC-001 is now true as written rather than narrowed. A second input class — an Azure DevOps URL carrying a fragment — was found still open when this item was first re-evaluated and was deliberately excluded from it then; it has since been ruled on by the same partner and is now covered by CHK033. With both rulings in place this item claims the whole of SC-001 again: no input class reaching the derivation produces a URL that fails to open while the control announces `Copy branch URL`
- [x] CHK015 - Does any requirement mandate a change that a success criterion claims will not happen? [Conflict-check, Spec §FR-008 vs §SC-006, data-model.md §Derived, non-persisted value] — the feature writes nothing and has no downstream consumer: the derived Branch URL is read only by the clipboard and the control's name, so "no figure changes" is structurally true, not merely asserted
- [x] CHK016 - Is the contradiction with the previous feature's requirement identified explicitly and resolved by a stated authority, rather than left for a reader to discover? [Conflict-check, Spec §"Relationship to feature 002", §Clarifications] — feature 002's FR-021 says the control copies "the exact branch text"; this spec supersedes that clause on the explicit original request and the approved design, preserves the rest of FR-021, and requires the documentation to follow (FR-010)
- [x] CHK017 - Do the edge cases and the success criteria agree, with no edge case permitting what a success criterion forbids? [Consistency, Spec §Edge Cases vs §Success Criteria] — SC-003 (branch name copied when no URL) and SC-005 (every input class covered) are exactly the edge-case list restated as outcomes
- [x] CHK018 - Are the surfaces in scope stated identically across the spec, the plan and the contract? [Consistency, Spec §FR-002/FR-008, plan.md §Project Structure, contracts/branchUrl.md §Caller contract] — all three say: one new helper module, one component region, one README sentence, nothing else
- [x] CHK019 - Is one artifact designated normative for the derivation rule, and do the places that restate it agree with it word for word in effect? [Consistency, contracts/branchUrl.md is normative and is referenced as such by plan.md §Design, data-model.md and quickstart.md] — the ordered normalisation appears in three places by design, each for a different reader: spec §FR-003 states it as a requirement, contracts/branchUrl.md §Stage 1 states it normatively with test vectors, research.md §R3 explains why the order matters. All three were compared line by line and agree, including the deliberate non-conversion of the explicit `ssh://` form. Any future change must land in the contract first
- [x] CHK033 - Is the outcome defined for an Azure DevOps repository URL that carries a **fragment** (including the legacy hash-routing form `https://org.visualstudio.com/proj/_git/repo#path=/x&version=GBmaster`)? [Conflict-check, Spec §SC-001 vs §FR-003e + §FR-005a, contracts/branchUrl.md §Stage 1 rule 6a] — **Resolved 2026-08-17 by a second human ruling**, recorded as the second Q/A in spec §Clarifications, Session 2026-08-17. It was genuinely open when this item was written: FR-003e then exempted Azure DevOps from the discard entirely, so FR-005a appended `?version=GB…` to the end of a fragment-bearing address and the parameter landed *inside* the fragment (`…/repo#readme?version=GBmain`), which a browser never sends as a query — SC-001's "100%" was false for that forge. The human partner verified the failure against the shipped module before ruling and chose to split the rule by URL component rather than by forge: a **fragment** is decoration on every forge and is always discarded; a **query** is decoration only on the path-shaped forges and remains addressing information on Azure DevOps, where FR-005a's preserve-and-append-with-`&` behaviour is unchanged. Evidence that this is now defined everywhere it needs to be: spec FR-003e (universal fragment clause) and FR-003's ordered list; spec §Edge Cases, the thirteenth entry, which spells out the `…#readme?version=GBmain` failure; contracts/branchUrl.md §Stage 1 rules 6a/6b/6c and four worked-example rows (Azure with a fragment, Azure with a query, Azure with both, and the legacy `visualstudio.com` hash form); tasks T016 (vectors, RED first) and T017 (implementation scope covering both shapes). SC-001 is therefore true as written for all four named forges, with no input class left undefined. The two rejected alternatives — assembling the Azure URL by component order, and declaring the class out of scope — are recorded with their reasons in the ruling
- [x] CHK020 - Does the contract's test-vector table agree with the spec's acceptance scenarios wherever both cover the same input? [Consistency, contracts/branchUrl.md §Worked examples vs Spec §User Story 1/3 scenarios] — GitHub, GitLab, Bitbucket, Azure DevOps, SSH form, `.git` suffix, trailing slash and `feature/x` appear in both with identical expected values

## Notes

- No item on this list is a post-launch metric; every one is decidable from the artifacts as they stand.
- **Superseded 2026-08-17.** The original note claimed that no item required a product decision from the human partner. That held for the pre-implementation pass; it stopped holding once post-implementation `speckit-analyze` found SC-001 and FR-003 + FR-005a mutually unsatisfiable for repository URLs carrying a query or a fragment on a path-shaped forge. That question *was* a product decision, it was put to the human partner, and the ruling is recorded in spec §Clarifications, Session 2026-08-17, with its evidence in `.specify/bridge/post-implementation-contradiction.md`. Everything else on this list was still answered by the approved design (`.specify/bridge/approved-design.md`), the constitution, or existing repository code.
- **CHK033 was the second such decision** — narrower, on an input class that predated and was untouched by the first ruling — and it was put to the human partner rather than decided by any agent. It was answered on 2026-08-17 and is now checked. **No item on this list is open.** Both rulings are recorded in spec §Clarifications, Session 2026-08-17, each with its rationale and its rejected alternatives.
- Neither ruling narrowed a success criterion. SC-001 keeps its text and its "100%" in both cases; the rulings changed the derivation rules so that the promise became true, rather than reducing what was promised.
